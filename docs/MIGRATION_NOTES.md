## Client patterns on 26.2 / Forge 65 (established in stage 4, reuse in stage 5)
- Event buses: before putting a listener in a class, check whether its event implements IModBusEvent (grep the Forge sources). Only those go in a bus = MOD class. RegisterKeyMappingsEvent, RegisterParticleProvidersEvent, AddGuiOverlayLayersEvent, RenderLivingEvent, InputEvent, ClientTickEvent are all game-bus events now. Simplest: leave out bus (default BOTH) and let Forge route each listener. With strictRuntimeChecks (on in our runs) a mismatch throws at mod construction; without it the listener silently never fires.
- HUD overlays: one layer, added in HudLayerHook.onHudLayerHookAddLayers (AddGuiOverlayLayersEvent, addWithCondition on the root stack, hidden with F1). To draw something new on the HUD, call its render(GuiGraphicsExtractor) from HudLayerHook.renderAll, as before.
- Drawing in GUI code: GuiGraphicsExtractor. text/centeredText (int positions), fill/fillGradient, blit(RenderPipelines.GUI_TEXTURED, texture, x, y, u, v, w, h, uW, vH, texW, texH, argb) with the tint/alpha as the last argument. pose() is a 2D Matrix3x2fStack (pushMatrix/popMatrix, translate(x, y), scale(x, y)). No RenderSystem state.
- Screens: override extractRenderState(...) instead of render(...); input is keyPressed(KeyEvent) and mouseClicked(MouseButtonEvent, boolean). The background pass (extractBackground) always runs, so a screen that wants no blur overrides it (AbilityMenuScreen, TextPromptScreen). Open with Minecraft.getInstance().gui.setScreen(screen); onClose()/removed() work as before.
- Particle providers: ClientParticleHandler (Dist.CLIENT, no bus param). registerSpecial(type, (options, level, x, y, z, xd, yd, zd, random) -> ...) for code-driven particles; registerSpriteSet(type, Provider::new) for JSON particles (Provider.createParticle has a RandomSource last argument).
- Textured particles: extend SingleQuadParticle, pass a sprite to the constructor, return SingleQuadParticle.Layer.TRANSLUCENT (or OPAQUE) from getLayer(), override getLightCoords for glow. ParticleFxParticle is the template; ParticleFx needs no change.
- Tick-only particles (logic, nothing drawn by the particle engine): extend Particle and return ParticleRenderType.NO_RENDER from getGroup() (ModelFxParticle).
- Custom geometry (stage 7): a ParticleGroup of our own per kind of particle, registered once with ParticleEngine.registerParticleGroup from ClientParticleHandler (guarded, never throws; getGroup() falls back to NO_RENDER if it failed). Particle-like geometry (ribbons): return a QuadParticleRenderState subclass with our own SingleQuadParticle.Layers (SlashRenderTypes; any SingleQuadParticle can also return SlashRenderTypes.ADDITIVE / TRANSLUCENT from getLayer()). Entity-like geometry (models with normals, lighting, overlay): a ParticleGroupRenderState that calls submitNodeCollector.order(n).submitCustomGeometry(...) with a RenderType (ModelFxRenderer). No frame pass (AddFramePassEvent) was needed.
- Textures for custom geometry go in the particle atlas (no mipmaps, any size) through assets/minecraft/atlases/particles.json, not the block atlas (Forge 65 keeps its mip level 4, so a texture side that is not a multiple of 16 crashes the client at load).
- A missing model or texture draws nothing (compare the sprite with atlas.missingSprite()); nothing at registration, setup or reload may throw.
- Key mappings: register in RegisterKeyMappingsEvent (game bus). One shared category, Keybindings.CATEGORY (circle_of_inevitability:main); a second Category.register with the same id throws.
- Client-only code reached from a common class (a server tick that reads a key, a packet handler that opens a screen) stays behind FMLEnvironment.dist.isClient(), as the client packets already do.

## Swing animations (new feature after stage 7, 2026-10-10; how-to in docs/ANIMATIONS.md)

- API found (26.2 / Forge 65), all read in the jars / Forge-patched sources:
  - First person: Forge fires RenderHandEvent(hand, poseStack, nodeCollector, packedLight, partialTick, interpolatedPitch, swingProgress, equipProgress, stack) before each hand in ItemInHandRenderer.submitHandsWithItems; a listener returns true to cancel (vanilla then skips submitArmWithItem for that hand). equipProgress is vanilla's inverseArmHeight. The swing math (swingArm / applyItemArmAttackTransform) cannot be changed from the event, so we cancel and draw: applyItemArmTransform is translate(side*0.56, -0.52 + equip*-0.6, -0.72), then the public ItemInHandRenderer.renderItem(entity, stack, FIRST_PERSON_RIGHT/LEFT_HAND, poseStack, collector, light). Renderer: Minecraft.getEntityRenderDispatcher().getItemInHandRenderer().
  - Third person: RenderPlayerEvent is now RenderAvatarEvent.Pre/Post (record; getState() is an AvatarRenderState with public int id = entity id, getRenderer(), getPoseStack(), getNodeCollector(), getCameraState()). LivingEntityRenderer.submit calls model.setupAnim(state) right away (for the layers) and the deferred model draw calls it again with the same state, so we change the render state, never the model parts, and never restore it in Post.

### Swing animations: tuning pass after the first in-game test (2026-10-10)
- Reported: first person the sword sat at the bottom edge, cropped and dark; attacks too fast; every move looked the same.
- Root cause of "every first-person move looks the same" (found by projecting every definition's keyframes through the hook's transform, the vanilla sword's firstperson_righthand display transform and the 70-degree hand projection in a scratch harness; read in ItemInHandRenderer / GameRenderer / Lighting of 26.2):
  1. The hook passed RenderHandEvent.getEquipProgress() (vanilla's inverseArmHeight) into its translate. ItemInHandRenderer.tick makes mainHandHeight follow the attack strength (getItemSwapScale), which every attack resets (hit or miss), so for the whole swing the hand was 0.3 to 0.6 blocks lower than vanilla's resting spot: the guard was on screen in only 0 to 12% of each swing, and every impact frame was the tip poking in at the bottom centre (y -0.5 .. -1.3, screen bottom = -1).
  2. The poses pitched the blade -60 .. -85 (pointing into the screen) and sampled yaw only -35 .. +70: the blade was mostly seen end-on. The hook applies roll, then yaw, then pitch, so the yaw sweep always turns in a plane containing the view direction: each cut drew a near-straight line through the hand. horizontal, diagonal_down and diagonal_up had the same yaw sweep and differed only by roll 0 / +35 / -35, which barely shows on a blade pointing along the roll axis.
  Not the cause (checked by reading): the hook used every channel (x, y, z, pitch, yaw, roll, scale) and the mirror flag (SwingAnimation.sample applies it); the sequence did advance on the client (SwingPlayer.onSwing; the headless run saw the cycle); no easing or blend flattened the values.
- Dark item: no lighting-argument bug. RenderHandEvent passes vanilla's own light (EntityRenderDispatcher.getPackedLightCoords), renderItem uses NO_OVERLAY and the FIRST_PERSON_* context like vanilla. The hand is drawn right after the level with Lighting.Entry.LEVEL (two fixed world light directions from above, diffuse floor 0.40) and world-space normals. The old poses showed the blade edge-on (face cos down to 0.03: mostly the dark outline pixels of the sword texture) and diagonal_down turned its flat downward (diffuse 0.40), at the bottom centre under the hotbar. Fixed by the poses: every wind-up and impact pose now shows the flat (face cos 0.31 .. 0.93, diffuse 0.54 .. 1.0; vanilla's resting sword: 0.70 / 0.62; the two lowest face values, vertical_down's impact and spin_slash's wind-up, are a blade pointing ahead seen from above, lit at 1.0 and 0.56).
- Decisions:
  - Pose.weight (0 = REST, 1 = in the swing; rises fast as a swing leaves rest, falls late as it returns). First person: vanilla's dip is multiplied by 1 - weight, the global offset and scale by weight, so a swing still leaves from and returns to exactly vanilla's spot. Public API only grew (a field, sample(progress, from)); every existing call works as before.
  - One global tuning block at the top of SwingAnimations: FIRST_PERSON_OFFSET_X/Y/Z = -0.18 / 0.24 / -0.25, FIRST_PERSON_SCALE = 1.2, SPEED = 1.0.
  - Every swing ~1.75x slower (8 -> 14 ticks, stab 7 -> 12, spin_slash 16) with four phases: wind-up IN_OUT (~4 t), cut OUT_EXPO (~2.5 t), hold OUT with a little drift (2 to 3 t), recovery IN_OUT (~5 t).
  - Blending: a swing that starts while another is on screen winds up from the old one's current pose (SwingPlayer.play captures poseFor(player, 0)); only the wind-up is blended, so no pose can stay stuck.
  - First-person poses re-made around itemRot(-110, yaw, roll): blade level, swept by yaw between about -70 (pointing right) and +80 (left) so the flat faces the camera at both ends, roll tilts the sweep, item(x, y, z) carries the travel. horizontal_reverse got its own keyframes: the mirror flag mirrors around the hand, which is right of the centre, and the mirrored cut ended with the tip off screen. Third-person arm values of the old five cuts kept, plus hold keys.
  - New moves: uppercut, spin_slash. The existing stab id was rewritten to the requested STAB (pull back to the hip, thrust along the view, recoil) rather than adding a second stab, so the WormOfTime sequence has 8 distinct ids.
  - /swinganim list prints every id with its length in ticks.
- Verified (2026-10-10): ./gradlew build before each of the three commits. Scratch harness (not committed; scratchpad only), run against the compiled classes: for all 8 moves, tip and guard on screen in 100% of the frames between start and end (old code: tip 51 .. 93%, guard 0 .. 12%), no NaN or infinite value; per move (ticks / cut direction on screen / tip at the impact): horizontal 14 / 179 deg / (-0.44, -0.40); horizontal_reverse 14 / 0 deg / (0.78, -0.42); diagonal_down 14 / -150 deg / (-0.34, -0.83); diagonal_up 14 / 151 deg / (-0.30, 0.45); vertical_down 14 / -111 deg / (0.12, -0.09); stab 12 / thrust toward the centre / (0.00, 0.06); uppercut 14 / 44 deg / (0.56, 0.77); spin_slash 16 / -176 deg over the top / (-0.69, -0.80) (screen x, y from -1 to 1). 20 of the 28 pairs differ in cut direction by 40 deg or more; the other 8 are at least 0.6 screen units apart at the start or at the end. Closest: horizontal / spin_slash (both right to left; starts 0.37 apart, ends 0.60, impact blade angle 19 deg, and the spin arcs over the top and is 2 ticks longer) and diagonal_up / spin_slash (both start low right, 0.19 apart; ends 1.43 apart, directions 31 deg). The near-still time at the impact is 2.3 .. 3.2 ticks. Blending: 576 interruptions (8 x 8 moves at 10 .. 90%) start exactly at the interrupted pose, equal the plain swing after the wind-up, no NaN. The sequence uses all 8 ids, never the same twice in a row (also wrapping around), reset 30 ticks. Third person (arm and held-sword tip from the model transforms): all 8 differ, closest pair 0.52 blocks apart on average. The four code snippets in docs/ANIMATIONS.md compile (after the DEEP_STAB definition they tell you to add).
